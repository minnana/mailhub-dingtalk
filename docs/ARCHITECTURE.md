# 实现结构

## 部署边界

只有 Nginx 发布主机端口，默认 18443。Nextcloud app 和 cron 共用数据与代码，但有独立资源限制。MariaDB 和 Redis 只连接 Docker 内部网络，不发布主机端口。证书任务是按需运行的容器，不常驻、不监听主机端口。

前端网络提供 app/cron 到邮箱服务商和钉钉的出站连接。Nginx 使用固定地址，Nextcloud 仅信任该代理；动态地址池与代理地址分开。域名、HTTPS 和高端口在代理配置中保持一致。内外 DNS 只改变入口 IP。

## 登录

1. 钉钉工作台打开域名根路径，代理跳转到插件接入页。
2. 接入页建立浏览器会话及一次性 begin nonce。钉钉内先向 `/begin` 发送受 CSRF 保护的 POST，退出旧会话并取得新的会话、认证 nonce 和 CSRF 令牌，然后调用固定版本钉钉 JSAPI 获取本企业应用授权码。普通浏览器不会自动执行退出步骤。
3. 浏览器以 POST 提交授权码、新认证 nonce 和新 Nextcloud CSRF 令牌；begin 与认证 nonce 用途隔离、只使用一次。
4. 后端使用服务端应用凭据取得应用 token，再向钉钉官方接口兑换 userid。
5. 验证允许的企业应用及人员范围，以 corpId 与 userid 的组合生成稳定用户映射；不按显示名、邮箱地址或前端传入身份登录。
6. 为该员工创建独立 Nextcloud 用户，通过版本限定的会话适配器完成正式登录、刷新会话标识并创建认证令牌。
7. 成功后仅跳转本站 Mail 页面。再次从钉钉入口打开时重新核验员工身份，避免共享设备继续使用上个人的会话。

本项目没有管理员共享密码登录员工的设计，也不直接写 Nextcloud 会话数据库。会话适配器已按 Nextcloud 34.0.5 接口核验；其他主版本尚未部署验收，每次升级核心版本都需要再次测试。

员工可在个人设置的“网页登录”中，使用新的钉钉授权码为同一映射账号设置独立本地密码。服务端验证当前用户、一次性用户绑定 nonce、CSRF、新授权身份及最新权限；调用 Nextcloud 原生密码 API，保留密码策略与哈希处理。成功或密码更新阶段出现异常后均撤销旧令牌并退出，以免旧会话继续使用。网页用户名使用原有稳定 UID，不按未验证邮箱生成别名；专属登录链接只预填用户名，不携带密码或登录令牌。原生网页登录继续执行账号停用和两步验证等规则。开启 Nextcloud 文件加密时，本功能拒绝无旧密码重设，避免损坏文件密钥。

## 邮箱与数据

邮箱绑定和凭据管理由 Nextcloud Mail 负责，插件不复制第二份 IMAP/SMTP 密码。Mail 保存所需授权信息，并通过原邮箱服务商收发。

本地会保留邮箱账号配置、邮件索引/预览、标记、部分缓存、草稿/发件队列和本地附件。原始邮件仍以服务商邮箱为准；移动或删除会同步影响原邮箱。恢复绑定关系需要同时恢复数据库和 Nextcloud 配置/实例密钥。

## 新邮件检查和通知

Mail 5.12.5 原版 `SyncJob` 会把配置的同步间隔限制到至少 300 秒，所以仅写入 `app.mail.background-sync-interval=60` 不能实现每分钟检查。本项目的 `FastSyncConfigurator` 只在 CLI、Nextcloud 34、Mail 5.12.5、目标间隔严格为整数 60 且 `app.mailhub.fast-sync-enabled=true` 时，调整同一个原生同步任务的内部到期门槛为 1 秒。**实际触发仍然是每分钟一次，不是每秒轮询邮箱。** Nextcloud 的 `CronService` 在一次运行中记录已经执行的任务 ID，同一 ID 不会在这一轮重复执行；原生锁和正数强制间隔行为保留。原 55 秒门槛可能在“上一轮靠后、下一轮靠前”时误跳一轮，此处去掉该多余等待。条件不满足时保留 Mail 原生调度；升级后须再次验证每轮去重和版本兼容。此调度适配不改写官方 Mail 源文件，和下文的 Sent 兼容补丁分开管理。

独立 cron 容器通过 BusyBox 每分钟调度 `cron-cycle.sh`，先执行官方 `cron.php`，再调用插件专属 `cli/notify-after-sync.php` 追加通知扫描。这样即使官方任务队列本轮先运行通知、后完成 Mail 同步，也能在整轮官方任务结束后再次发现新增并尝试发送。上一轮完整周期尚未结束时，不会再启动同一条 cron 命令；每个账号仍受队列、同步耗时和服务商限流影响。追加扫描等待的是整轮官方任务结束，不是每个账号同步结束的独立回调。

每轮去重依据为已部署版本的 [Nextcloud 34.0.5 CronService](https://github.com/nextcloud/server/blob/v34.0.5/core/Service/CronService.php#L169-L176)。内部到期门槛和任务触发频率是两件事；不要把本适配带入“每秒启动 cron”的其他部署。

另有独立的 Mail 5.12.5 兼容补丁：现场腾讯“已发送”文件夹在未选中时返回空 STATUS 元数据，Horde 生成空同步 token，继而把“缺少 UIDVALIDITY”误认为“UIDVALIDITY 变化”，反复清本地缓存并全量重拉。补丁仅在 token 为空时，以 EXAMINE 只读选择文件夹再取元数据，覆盖初次和增量同步；真正非空 UIDVALIDITY 的变化仍按官方逻辑处理。它不改邮箱内容、已读标记或通知游标。该补丁确实修改一个官方 Mail 文件，与上面的无源码调度适配不同；版本、原始与修改后 SHA 均严格检查，原件在应用目录之外保存。维护和恢复说明见 [维护手册](OPERATIONS.md)。

通知 Job 读取 Mail 已同步的 INBOX 元数据，复核账号归属及员工状态。按账号、文件夹、UIDVALIDITY、UID 保存高水位，首次绑定/启用建立基线。基线之后新同步的邮件无论已读或未读都计入，已删除和草稿仍排除；不扫描垃圾箱或其他文件夹，也不导出邮件正文和附件。仅改变已读状态不会重复通知，移入 INBOX 后获得新 UID 的邮件则可能被视为新增收件。

默认 `notification_digest_seconds=0`，取值范围 0–3600 秒；零表示立即将本次已发现的新增邮件按员工合并提交，不再额外等待摘要窗口，既有显式值保持不变。原通知任务间隔仍为 55 秒，为每分钟 cron 提供调度余量；追加 CLI 入口不再等待该任务的下一次到期。每人同一时间最多一个待提交摘要；已经提交、正在等待回执的摘要不会阻塞后续新邮件。两个入口先后处理不同新邮件时，不保证每分钟只有一条通知。等待调度、同步、其他后台任务和钉钉接口仍会耗时，这不是 55 秒或 60 秒送达保证。

两个入口共用 `NotificationRunner`，在 Nextcloud `datadirectory` 下的 `.mailhub-dingtalk-notify.lock` 上取得非阻塞独占 `flock`。锁忙时立即安全跳过，不记为故障；真实失败记录固定脱敏错误。文件为运行用户所有、0600、普通单硬链接文件，释放锁后保留文件及其 inode，不能运行中删除重建。该锁只适用于同一 Linux 主机上 app/cron 共用本地数据挂载，不支持跨主机高可用。原 `NotificationJob` 的禁止并行执行设置与 Mail 自身同步锁仍保留。

发送前及取得应用令牌后，直接重读必要的权限记录，重新核验人员映射、员工启用状态、通知偏好和配置代次，避免旧缓存掩盖停用。此步骤不主动连接 IMAP 验证邮箱授权是否仍有效。调用钉钉个人工作通知接口后，取得任务编号仅代表“已提交”；后续查询该员工结果后才记录“已送达”。队列状态使用有条件更新；撤销与外部请求同时发生时，迟到的成功或失败不能把已撤销批次重新激活。

明确被拒绝的请求按策略退避重试；发生网络超时、已提交但无法确认结果等情况记录“结果不确定”，不盲目重复发送。停用员工后取消未提交任务，但不能把已发出的消息称为已撤回。终态投递记录按当前策略保留 90 天，高水位保留以避免重复。

当前通知链接进入邮箱应用，不保证精确定位到某一封邮件；摘要可能包含多封邮件。要增加精确邮件跳转，必须继续复核 Mail 路由、消息归属及邮件被移动/删除后的处理。

## 管理员控制台

所有管理接口保留 Nextcloud 管理员权限检查，写操作保留 CSRF。控制台显示配置是否完整、人员映射、绑定地址、最近登录、通知与后台状态；不返回应用秘密或邮箱密码。

全局暂停新登录不会终止所有已有会话。停用单个员工会同时禁用用户及撤销认证令牌。当前未接入钉钉离职事件订阅，因此管理员必须完成离职停用操作。

## 证书和公开源码

支持 DNSPod API，也支持 acme-dns。后者先注册单一验证子域，再由域名所有者添加一次 `_acme-challenge` CNAME；续期只更新该验证子域的 TXT，无需把整个 DNS 平台的 API 密钥交给服务器。

证书、私钥、ACME 状态和应用凭据全部位于 runtime。共享源码包只包含通用模板。公司实际部署交接记录可另存于被 Git 排除的 `deployment-private/`，但仍不应写入明文密码。
