# 从空白服务器到首封通知

这是一条阅读和执行路线，面向第一次部署的管理员。所有安装命令以 [部署手册](DEPLOYMENT.md) 为准，日常操作以 [维护手册](OPERATIONS.md) 为准；本页不复制同一套脚本命令，避免两份教程更新后不一致。

项目仓库：[minnana/mailhub-dingtalk](https://github.com/minnana/mailhub-dingtalk)。部署在自己的 Ubuntu 服务器上，不是导入钉钉后就能运行的托管服务。管理员需要服务器、DNS 和钉钉内部应用的管理权限；员工随后分别绑定自己的邮箱。

## 先准备一张私有部署记录

记录以下信息，供管理员在现场填写；**真实密钥不要写进 GitHub、公开文档、Issue 或聊天**。

| 准备项 | 示例或用途 |
|---|---|
| 服务器 | Ubuntu 24.04，固定内网地址；有业务时先盘点已有端口、Docker 网络和资源 |
| 唯一访问地址 | `https://mailhub.example.com:18443/`；电脑、手机、内外网使用同一个地址 |
| DNS 权限 | 维护公共 A 记录、内部同名解析，以及证书验证 CNAME |
| 网络路径 | 公网 TCP 18443 到主机同端口；服务器可访问邮箱、钉钉、镜像及证书服务 |
| 容器网段 | 两个不与主机、VPN 或已有 Docker 网络重叠的私有 `/24` |
| 钉钉应用 | 本企业 CorpId、内部应用 AppKey/Client ID、AppSecret、AgentId，试点员工 UserId |
| 试点邮箱 | 至少两名员工各自的账号；由本人掌握授权码或完成 OAuth |
| 恢复准备 | 独立备份文件系统、受限异机副本和后续隔离恢复环境 |
| 软件来源 | 本次部署的完整 Git 提交号；镜像摘要和 Mail 校验值使用随版本提供的清单 |

只有局域网试点时可以暂不开放公网；手机使用移动数据时必须有可达的外网路径。Gmail OAuth 还需要单独配置 Google 项目和网络，不能把普通 IMAP 邮箱绑定成功视为 Gmail 已完成。

## 按顺序完成八步

| 步骤 | 阅读与执行位置 | 本步应达到的结果 |
|---|---|---|
| 1. 判断主机类型 | [部署手册第 1 节](DEPLOYMENT.md#1-确认部署条件) | 空白主机先安装工具及 Docker；已有业务主机只检查，不重装或重启 Docker |
| 2. 规划资源和入口 | 部署手册第 2–3 节 | 端口与网段无冲突；DNS、端口映射及证书验证方式确定 |
| 3. 下载并初始化 | [部署手册第 4 节](DEPLOYMENT.md#4-放置源码并初始化) | 从 GitHub 获取已审阅提交，初始化 `/opt/mailhub/runtime/`；密码未进入源码 |
| 4. 配置证书 | [部署手册第 5 节](DEPLOYMENT.md#5-注册-acme-dns-并添加一次-cname) | 注册一次 acme-dns、添加自己的 CNAME，完成 DNS 验证；或使用受限 DNS API 凭据 |
| 5. 启动并检查 | [部署手册第 6 节](DEPLOYMENT.md#6-签发证书并开放应用) | HTTPS 无证书警告，本地管理员能登录，基础健康检查通过 |
| 6. 接通钉钉 | [管理员手册](ADMIN-GUIDE.md) | 网页能力、所需权限、安全设置、可见范围、版本发布和本项目允许名单均完成；试点员工免登成功 |
| 7. 绑定和验收 | [员工手册](USER-GUIDE.md)及部署手册第 8 节 | 本人绑定邮箱；两名员工数据互相隔离；实际收发、附件和自然通知经过验证 |
| 8. 建立维护机制 | 部署手册第 7 节及 [维护手册](OPERATIONS.md) | 续期检查启用，外部备份实际成功，隔离恢复有记录 |

运行 `start.sh --prepare-only` 是等待 DNS 时的可选准备步骤，不会创建新的公开入口。初始化完成但钉钉配置仍关闭时，员工入口无法使用是预期行为；先使用 `/index.php/login` 登录本地管理员，再按第 6 步配置。

每完成一步保存成功结果和遇到的问题；不要通过关闭 TLS、扩大文件权限、清空数据库预留或强制重建正在工作的容器来跳过故障。

## 第一封通知应该怎样测试

1. 员工在钉钉内首次登录，绑定自己的邮箱，等待收件箱出现邮件并建立通知基线。初次同步的历史邮件不会逐封推送。
2. 关闭邮箱页面，再从另一个邮箱投递一封新的测试邮件。应保留发信、到达服务商、后台同步、接口投递与客户端收到的时间。
3. 等自然后台周期处理，不通过反复手动触发通知来证明自动调度。默认每分钟运行一次完整周期，完成官方后台任务后追加扫描，将当前新增按员工合并提交，不额外等待摘要窗口。
4. 在钉钉电脑端和手机端分别确认收到通知并能进入邮箱；再用第二名员工确认看不到前一名的账号和邮件，通知也只到对应员工。
5. 实际验证发信、回复和附件。若员工还使用普通网页，按员工手册单独设置网页登录密码；它与邮箱服务商密码不同。

一分钟是调度频率，不是 60 秒端到端送达保证。新 INBOX 邮件即使被其他客户端标为已读也会纳入提醒；删除、草稿、垃圾箱和其他文件夹不在当前提醒范围，首次或重建基线不会补推历史。更完整的时序、锁与排障见维护手册。

## 哪些结果不能互相替代

- 基础健康检查通过，不代表外网映射或钉钉客户端已经通过。移动数据和公司 Wi-Fi 要分别实测。
- 钉钉免登通过，不代表邮箱已授权；每位员工首次仍需绑定自己的账号。
- 钉钉接口接受任务，不代表员工已看到通知；需结合结果查询和真实客户端。
- 证书续期定时器已启用，不代表已经发生过一次到期续签；观察执行记录和证书日期。
- 备份文件及校验正确，不代表可用恢复；演练必须事先阻断到真实邮箱和钉钉的出站连接。
- 小范围试点成功，不代表 200 人容量已验证；按实际账号数分批扩大，观察同步积压和资源。

上线后以 [维护手册](OPERATIONS.md) 为操作入口，以自己的私有变更记录为现场依据。本仓库的 [验收记录](VALIDATION.md) 只说明已经测过哪些边界，不能代替新部署的独立验收。
