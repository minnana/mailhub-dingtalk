## 已观察到但未阻断基础服务的情况

### 公网回程修复

原公网连接超时定位为旁路网关环境的回程路径问题。已只针对 Mailhub 代理容器和 TCP 源端口配置策略，保留主表的非默认具体路由，不修改宿主机原默认网关；独立 systemd 服务已启用，实时状态为 `applied`。用户已确认移动数据、Wi-Fi 和电脑可打开。方案及恢复边界见 [回程路由说明](RETURN-ROUTE.md)。

### 邮箱参数自动发现修复

自动发现失败定位到两个因素：旧旁路 DNS 的 MX 查询超时，以及 Mail 5.12.5 的自动发现流程会继续尝试多个站点。修复仅调整 app / cron 两个应用容器使用的 DNS 解析器，并通过 Nextcloud 提供的中间件扩展点，优先识别七类国内邮箱的固定参数；没有改主机或 Docker 的全局 DNS。

七类参数为腾讯企业邮箱、QQ / Foxmail、网易 163、网易 126、网易 Yeah、阿里企业邮箱和阿里云个人邮箱。企业邮箱域名通过明确的 MX 记录识别；不能确定的情形保留原发现流程。真实注册检查确认身份认证、CSRF 和限流中间件仍先执行。

普通用户在原自动发现 URL 上的 16 项 HTTP 检查通过。其中，企业邮箱域名通过 MX 识别为腾讯企业邮箱的一次请求约 0.09 秒，QQ 邮箱一次请求约 0.038 秒。这些自动化检查仅验证参数发现，未获取用户邮箱密码，也未代替用户绑定账号。

随后员工本人重试并确认已进入邮箱列表；早期只读快照显示 `mapped_employees=1`、`completed_logins=1`、`bound_mailbox_count=1`，确认一个实际腾讯企业邮箱已绑定。员工随后继续添加其他邮箱，因此这些数量仅代表当时快照，不是最终总数。

### 一分钟调度和新增邮件通知规则（早期联调记录）

本小节保留 17 时阶段的历史调度与摘要配置，供理解问题定位过程。当前运行值已变更为内部到期门槛 1 秒、实际每分钟调度、摘要窗口 0；最终自然周期验收见本文开头的“本轮自查与修复”，不要照本节历史数值重新配置。

Mail 5.12.5 原版把同步间隔限制为至少 300 秒，仅设置 60 秒不会生效。此前已部署受版本和配置检查的 `FastSyncConfigurator`：在 CLI 启动阶段调整同一个原生 `SyncJob` 实例为 55 秒，为每分钟 cron 与严格大于判断留出余量，保留 Mail 原有同步和锁逻辑。下述早期观察时，实际同步目标为整数 60，摘要窗口为 60 秒，专用 cron 容器内 crontab 已核对为每分钟；零额外等待版本另列。

当时的真实容器集成检查验证有效间隔为 55 秒、核心 JobList 构建任务时使用同一实例、强制间隔及跳过标志符合预期，且检查前后官方 `SyncJob` 文件哈希不变。该检查没有执行 IMAP 同步或写入任务队列。完整健康检查及本节所列回归测试通过。17:32 的自然调度中，三个 Mail 原生同步任务确实执行，耗时分别约 16、6、5 秒。

随后观察到两个连续自然周期：三个同步任务的 `last_run` 分别从 17:35:00、17:35:21、17:35:16 更新为 17:36:00、17:36:17、17:36:13，对应间隔 60、56、57 秒；通知任务从 17:35:26 更新为 17:36:24，间隔 58 秒。未发现预留锁遗留，单任务耗时约 4–16 秒。**这只确认所测两个周期的执行，不构成长期周期上限、200 人容量证明或 60 秒端到端送达承诺。**

新规则会计入基线之后新同步的 INBOX 邮件，即使它已被其他客户端标记已读；已删除和草稿仍排除。初次基线不推历史，垃圾箱和其他文件夹未纳入。已有基线没有因本次默认间隔或已读规则调整而清空。

第一封确认测试邮件此前已被其他客户端标记已读，因此曾被旧的未读筛选跳过。为核对这一明确的测试事件，本次对其做了一次性、带去重的补入；**这不是新规则自然触发的证据，也不是历史邮件批量补推**，不公开邮件 UID 或收件人标识。

另一个实际新增邮件已由自然 cron 扫描入队并提交钉钉，先记录为 `submitted`，随后 **17:32:27** 的自然结果查询确认 `delivered=1`。这是独立于上述人工补入的自然流程观察；当时剩余的一条待发事件属于人工恢复的单封测试，不能混作另一条自然新信。

### 提醒链接修复与点击边界

原普通 HTTPS 链接曾跳出钉钉。第一版修复使用 `dingtalk://dingtalkclient/page/link` 和 `pc_slide=true`；用户随后已通过真实提醒和截图确认电脑右侧页面能够完成免登。但用户要求直接进入应用工作区，因此又部署了按设备区分的链接，而非将侧边成功算作最终目标已完成。

### 取消额外摘要等待的版本

用户报告过一封邮件从发出到提醒约三分钟。为减少调度顺序和摘要窗口造成的等待，新版本默认 `notification_digest_seconds=0`；每分钟运行完整周期，先执行官方 `cron.php`，完成后再调用专属 `notify-after-sync.php`，按员工合并当时已发现的新邮件并尝试发送，不再额外等一分钟。两个通知入口共用本地数据目录上的互斥 Runner，避免同时处理。

代码和预部署测试通过后，实际部署已核对同步目标为整数 60、摘要设置为 0，crontab 每分钟调用完整周期，完整健康检查通过。真实追加 CLI 返回 OK，共享锁文件为 UID 33、0600 的空文件；自然日志在 18:03:10 和 18:04:10 均记录追加扫描成功。预部署的模拟通知服务与假 PHP 测试没有发送消息，真实 CLI 与自然任务则属于生产处理路径，二者分开记录。

解除占用后，原受阻任务在 18:08:00 的自然周期运行约 15 秒并正常释放预留，另两个同步任务随后各约 5 秒。18:08:20 的同轮原通知 Job 已直接为该新测试邮件建立摘要并取得 `submitted`，发送尝试为 1、无错误；18:08:25 追加扫描日志为 OK，没有重复事件，三个同步任务的预留均为 0。它证明恢复后本轮不再额外等待摘要窗口，不能误写为由追加扫描首次发送。

该命令通过后，仍需在自然 cron 运行期间观察多轮任务时间，并用基线建立后的新邮件核对实际提醒；不要把人工补入或手动运行任务写成自然调度结果。

### 内外网 HTTPS 对照

在管理员终端把示例域名换为自己的部署域名，按提示填写内网地址。这里只读取状态接口，不提供密码、令牌或员工信息：

```bash
MAILHUB_HOST=mailhub.example.com
MAILHUB_PORT=18443
read -r -p '输入应用服务器内网 IPv4 地址: ' MAILHUB_LAN_ADDRESS
curl --fail --show-error --connect-timeout 10 --max-time 30 \
  --resolve "$MAILHUB_HOST:$MAILHUB_PORT:$MAILHUB_LAN_ADDRESS" \
  "https://$MAILHUB_HOST:$MAILHUB_PORT/status.php"
```

再从办公室网络之外的终端执行不带 `--resolve` 的请求，并用关闭 Wi-Fi 的手机检查同一个地址：

```bash
curl --fail --show-error --connect-timeout 10 --max-time 30 \
  'https://mailhub.example.com:18443/status.php'
```

不要加 `-k`。内网指定地址成功而公网超时，只能把范围缩小到 DNS/外部路径等后续检查，不能直接判定一定是哪台防火墙或运营商造成。

### HTTP 权限和真实业务回归

本轮执行了 24 项真实管理员/HTTP 路径检查及 27 项两名临时员工的网页权限检查；较早的 17 项管理员/登录、4 项普通用户和 16 项自动发现检查另作历史记录。公开仓库不附带管理员登录 Cookie、密码或临时会话脚本。重新验证时，应使用本次部署自己的测试会话，按下列范围记录结果：

- 匿名访问插件入口、登录准备接口及管理接口的预期行为。
- CSRF 请求令牌、登录准备前后会话/nonce 变化及错误请求的拒绝行为。
- 管理员访问管理功能、普通用户被拒绝访问管理功能。
- 普通用户通过 Mail 原有自动发现 URL 获得已知提供商参数；同时验证身份、CSRF 和限流边界仍有效，不提交邮箱密码或执行账号绑定。
- 测试用户和会话的清理；不要把权限测试账号长期留在生产系统。

随后执行 [部署手册](DEPLOYMENT.md) 的分阶段验收，用真实员工、真实邮箱及客户端完成上述未验收事项。钉钉应用令牌、邮箱 TLS 探测和模拟测试都不能替代这一阶段。

版本、部署配置或业务代码发生变化后，应记录新的测试日期、代码版本、执行范围和结果，不把本次结果自动沿用到后续版本。
